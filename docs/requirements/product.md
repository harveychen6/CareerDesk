# 产品需求：CareerDesk

更新日期：2026-11-25（北京时间）。本文是产品总需求，同时维护下一轮技术方案与实施进度。

版本边界：第 2～10 节记录现有 MVP 基线，不代表下一轮已经实现；第 12～16 节定义下一轮「岗位定制简历」。下一轮涉及岗位分析、项目状态、版本与生成行为时，以新章节为准。原 MVP 技术文档中的关键词计分和投递版动态引用仍是旧实现，不能直接作为下一轮验收标准。

## 1. 定位

CareerDesk 面向技术求职者，把日常项目、实习和工作材料整理成真实经历，再生成对标目标岗位 JD、可编辑、可直接投递的简历。核心链路是「零散材料 → 用户确认的事实 → JD 对照与经历选择 → 岗位定制简历」。

核心交付是一份岗位简历。日常积累降低重复整理成本，但不是首次使用的前置条件；用户可以带着旧简历、项目说明和 JD 直接开始。产品不扩展成通用聊天助手、完整项目管理系统或全流程招聘平台。

它同时是作者自己的日常工具，和一份可以公开克隆的开源项目。使用者在本机运行应用。没有账号，没有多人协作，没有作者托管的网站。

核心原则：

- **事实与成果分开。** 计划中、进行中、已完成是三种状态。规划不能写成已经达成的结果。
- **证据留在项目里。** 事实、数据、链接和待补问题先记在项目上，简历句子从这些材料里来。
- **母版与投递版分开。** 经历母版全局只有一份。投递版按岗位派生。投递版上改过的句子留在该版本里。
- **导航少。** 工作台只有项目、岗位、简历三个页面。高频操作在一两步内完成。

第一版界面语言为中文。文案集中维护，不在各组件里散落硬编码句子。不做多语言。

## 2. 信息架构

全局左侧栏固定三个入口：

1. **项目（素材库）**：进度看板和经历素材。
2. **岗位（目标库）**：目标 JD 与匹配结果。
3. **简历（编辑器）**：经历母版、投递版裁剪、导出。

布局跟随原型：左侧栏，而不是顶部三个 Tab。侧栏展示档案姓名，以及两个派生进度：

- 素材完整度 = 已写事实且没有待补问题的项目数 / 项目总数
- 投递准备度 = 已有投递版的岗位数 / 岗位总数

进度不单独入库。没有项目或岗位时，进度显示为空状态，不显示百分比。

## 3. 概念

| 概念 | 使用者能感知的内容 |
| --- | --- |
| 档案 | 姓名、抬头、年限、城市、联系方式、个人简介、技术栈、教育经历。第一次打开是空的 |
| 项目 | 标题、状态、摘要、技术标签、事实与证据、待补问题、简历描述、所属团队、起止时间 |
| 岗位 | 公司、岗位名称、JD 原文。城市、薪资、部门可空。另有关键词、匹配分、匹配到的项目 |
| 简历版本 | 母版全局一份。每个岗位最多一份投递版。版本里记录勾选了哪些项目，以及该版本自己的句子 |
| 合并提案 | 母版当前句子，与根据最新事实生成的新句子。计划中的项目不进入提案 |

城市、薪资、部门只用于岗位展示。匹配不依赖这三项。

## 4. 项目页

三列看板：计划中、进行中、已完成。卡片可拖拽改变状态。支持按名称或技术标签搜索。右上角可新建项目。没有项目时，看板各列为空，并提供新建和「导入示例数据」两个动作。

点击卡片，右侧滑出抽屉，自动保存，只包含：

1. **状态**：计划中 / 进行中 / 已完成。
2. **做了什么 & 证据**：Markdown 文本。记录背景、行动、数据、截图链接或 Git 记录。
3. **待补问题**：一行一条。记录缺的量化指标或未闭环的细节。
4. **简历描述**：准备放进简历的句子。可点击「AI 提炼」，从事实生成。

状态旁的说明：

- 计划中：不进入简历正文，只能作为技术栈了解项。
- 进行中：简历中必须能看出尚未完成。
- 已完成：可以写入成果，量化数据需要能在事实里找到。

「AI 提炼」在计划中项目上不生成成果句，只生成筹备中、尚未执行的说明。没有配置模型时，按钮不可用，并说明原因。已写好的事实和简历句仍可手改。

卡片展示标题、更新时间、摘要、标签、状态，以及待补问题数量。

## 5. 岗位页

左侧是岗位列表：公司、岗位名称、匹配度。右侧是详情和匹配区。列表按匹配度从高到低。

添加岗位时填写公司、岗位名称，并粘贴 JD 原文。城市、薪资、部门可选。保存后提取 3～5 个关键词，并与项目库计算匹配。

关键词标出两类：

- 项目的标签、事实或简历句里能找到原文
- 找不到原文，视为证据待补充

右侧列出最相关的 2～3 个项目和匹配原因。计划中的项目可以出现，并标明尚未执行。匹配原因要引用项目事实中的原句。

匹配度颜色：80 分及以上为绿，65–79 为黄，低于 65 为灰。分数来自规则，不由模型直接给定。

主操作是「生成投递版简历」。该岗位已有投递版时，打开已有版本。没有配置模型时，可以保存 JD，不能提取关键词和匹配原因。

## 6. 简历页

三栏：左侧版本，中间勾选，右侧预览和导出。

左侧置顶「经历母版」，下面是各岗位的投递版。

中间列出全部项目。投递版默认勾选该岗位匹配结果中状态不是计划中的项目。勾选计划中或进行中时，显示：

> 该项目尚未完成，建议在简历中标注进行中或仅作技术栈展示

右侧按勾选结果渲染简历：抬头来自档案，项目句子来自当前版本。投递版正文可以直接修改。修改只保存在当前投递版。母版纸面不可直接改写，句子通过项目简历描述和合并更新。

导出：

- **Markdown**：下载当前版本的文本。
- **PDF**：打开与预览同一套版式的打印页，由浏览器另存为 PDF。

未勾选的项目不出现在导出结果里。

档案为空时，预览仍可排版，抬头处显示待填写，并链到档案编辑。档案编辑放在简历页内，不新增第四个主导航。

## 7. 旅程

### 日常记录

打开项目，进入卡片，补充事实或待补问题，关闭抽屉。内容已自动保存。

### 同步母版

触发：

- 项目进入「已完成」，且事实比上次同步到母版更新。
- 打开应用时，距离上次同步超过设置的间隔，并且项目事实有更新。间隔默认 7 天，可在设置中修改。不绑定星期几。

出现横幅：「检测到 X 个项目有新进展，是否更新到经历母版？」

「查看并合并」打开左右对比：左边是母版当前描述，右边是依据最新事实生成的描述。计划中的项目被标为已忽略，不参与合并。

确认合并后，只更新经历母版。已经在投递版里改过的句子保持不变，并提示母版有更新，由使用者决定是否同步到该投递版。

没有配置模型时，不生成新的合并提案。已有的手工简历句仍可在项目抽屉里编辑。

### 针对岗位出简历

粘贴 JD，查看匹配到的项目，生成投递版，在简历页调整勾选和措辞，导出 Markdown 或 PDF。

## 8. 模型约束

凡是生成简历描述、合并候选句或匹配原因的请求，系统提示都包含：

> 仅基于提供的事实和证据进行提炼，严禁编造未提及的数据，严禁将「计划中」的事项描述为已达成的结果。

产品层拒绝这些结果：

- 句子中的数字在事实里找不到，且不能由事实中的两个数复核。
- 计划中项目被写成已达成结果。
- 进行中项目被写成已经全量上线，或句子里看不出「进行中」。

被拒绝的合并候选不能确认写入母版。

调用模型时才会把事实、待补问题和 JD 原文发往使用者配置的模型服务。看板、编辑、计分规则、Markdown 导出和 PDF 打印不访问该服务。

## 9. 示例数据

默认数据库是空的：空档案、空项目、空岗位、一份空白母版。

应用提供「导入示例数据」。示例使用原型中的虚构人物与项目，只用于演示三列看板、匹配和简历版式。导入前若库中已有内容，需要明确确认会写入示例，避免盖住真实档案。示例数据不是安装后的默认内容。

## 10. 验收

- 新建项目、拖拽改状态、刷新后事实仍在。
- 计划中项目的提炼结果不含成果数字；进行中项目的简历句含「进行中」。
- 改一份投递版的正文后，母版和其他岗位版本不变。
- 生成投递版时，计划中项目默认不勾选。
- 合并母版后，已有手工改写的投递版句子不变。
- 未配置模型时，可以记录项目、编辑简历、导出 Markdown 和 PDF。
- 首次启动看到空状态，而不是虚构人物的职业档案。

## 11. 不在本版

账号、多人协作、作者托管的在线服务、安装包、富文本编辑器、向量检索、定时邮件、在线分享链接、多语言、插件市场。

## 12. 下一轮：岗位定制简历

### 12.1 目标与现状

本轮目标：用户提供完整 JD 和已有项目材料，经过少量确认，获得一份有事实依据、针对该岗位组织重点、可以编辑并导出的简历。

当前实现已经具备项目记录、关键词匹配、投递版编辑和 Markdown/PDF 导出。但 `src/server/ai/prompts.ts` 中的项目提炼不接收 JD，`src/server/resumes.ts` 主要根据匹配结果勾选项目；尚未实现完整 JD 驱动的岗位描述生成。这是本轮要补齐的主链路，不能把现有「生成投递版」当作本轮已经完成。

第一批目标用户：有真实技术项目、实习或工作经历，但材料分散、不知道如何选重点或针对岗位改写的人。没有相关经历时，产品可以说明当前材料不足，不能凭空生成岗位经验。

### 12.2 两种入口，一条交付链路

- 临近投递：在岗位页粘贴 JD，选择已有项目或粘贴旧简历、项目说明、周报等纯文本材料，确认事实后生成初稿。
- 日常积累：在项目页记录事实；进入某个目标岗位后复用已有素材，不重复录入。

主流程：粘贴 JD → 选择或补充材料 → 查看初稿及关键待确认项 → 按需补充、接受改写 → 编辑与导出。

保持项目、岗位、简历三个主导航。材料整理嵌在项目抽屉和岗位生成流程中；适配建议嵌在简历编辑器中，不新增独立报告页、题库或聊天页。经历母版继续保留，但无需先整理母版才能生成岗位稿。

### 12.3 本轮必须交付

1. **纯文本材料整理。** 保留用户原文，将模型整理结果作为候选事实，展示原文出处；用户确认后才成为生成依据。首版不读取任意本地路径，不自动抓取链接，不解析 PDF/Word，不自动扫描代码仓库。
2. **完整 JD 分析。** 提取职责、必要条件、优先条件、背景条件及原文位置，保留「且/或」关系。不再只靠 3～5 个关键词解释岗位。
3. **要求与事实对照。** 区分直接证据、可迁移证据、材料未说明、用户确认没有相关经历。模型不能凭空判定用户不会某项能力。
4. **岗位描述生成。** 推荐经历及顺序，依据完整 JD 和确认事实生成岗位专属描述，压缩次要内容；不能仅复制通用项目句、堆砌 JD 术语或调整项目勾选。
5. **少量针对性补问。** 一轮最多展示 3 个影响当前简历的问题，可回答「不清楚」「没有做过」或跳过。材料足够先出初稿，缺少量化指标不阻止保守描述。补问后仅显式重新生成，禁止无限自动追问。
6. **建议直接作用于简历。** 显示原句、建议句、相关 JD、事实来源及修改理由，支持逐条接受、编辑或拒绝；首次尚无旧稿时展示建议稿，不制造空白对比步骤。
7. **版本稳定与导出。** 岗位稿有独立内容快照，素材和母版变化只提示；确认投递时冻结快照，后续修改进入工作稿。预览、Markdown 和打印页读取同一个文档模型。

### 12.4 事实与成果边界

- 用户确认表示用户认可材料，不能宣传为独立核验或客观真实性认证。
- 项目仍在进行，不代表其中所有贡献都未完成。允许描述已完成的子任务及已验证结果，同时保留整体「进行中」边界；不能将局部上线写成全量交付。
- 计划中的项目不进入默认推荐和成果生成。用户手工加入时保留尚未执行说明，不能借此增加能力覆盖。
- 数字必须对应原事实的指标、单位、对象、时间和条件。不能因为数字曾在材料中出现，就挪到另一项成果里。
- 首版 AI 改写不自动推导新百分比；需要推导时由用户明确确认包含算式与口径的新事实，再作为依据。替代旧版「任意两个数字可以推导百分比」规则。
- 不能把团队成果写成个人成果，不能把参与写成主导，不能把 JD 要求写成用户已做过的工作。
- 标签、旧简历句和模型整理结果可用于寻找材料，不能未经用户确认自动升级成可信事实。
- 手工编辑始终可用；存在风险时提示确认。程序校验不等于完整语义证明，不承诺绝对防幻觉或过筛概率。

### 12.5 范围取舍

| 能力 | 本轮决定 |
| --- | --- |
| 项目素材、岗位、简历编辑 | 保留并贯通 |
| 适配判断与修改建议 | 合并进生成与编辑，不做独立长报告 |
| 关键词匹配分 | 旧数据保留，不作为新主流程的胜任度结论或默认排序依据；以要求与证据列表替代 |
| 经历母版自动同步 | 保留旧能力，不扩大；不能静默更新岗位稿 |
| 公司调研、通用聊天、情绪支持 | 本轮不做 |
| 全量投递看板、统计、招聘网站自动填写 | 本轮不做 |
| 独立题库、学习中心、模拟面试 | 后续评估；不纳入本轮验收 |
| 简历主张的少量面试追问 | 后续扩展，不阻塞本轮发布 |
| 对方 CareerDesk 集成 | 本轮不合并源码；保留 JD、简历 Markdown 和投递快照作为未来交接基础 |
| 安装包、新模板市场、向量库、多模型路由 | 本轮不做 |

## 13. 下一轮技术方案

### 13.1 架构与模块边界

沿用 Next.js、TypeScript、SQLite、Drizzle、Zod 和现有兼容模型接口。模型密钥仅在服务端使用；不引入 Agent 工具循环、后台队列、搜索服务或新数据库。调用当前用户配置的模型，缓存相同输入，降低重复成本。

```mermaid
flowchart LR
  Material[粘贴材料或已有项目事实] --> Confirm[候选整理与用户确认]
  Confirm --> Facts[确认事实与原文引用]
  JD[完整 JD] --> Requirements[岗位要求及原文引用]
  Facts --> Assess[要求与事实对照]
  Requirements --> Assess
  Assess --> Draft[岗位稿建议]
  Facts --> Draft
  Draft --> Guard[结构与事实风险检查]
  Guard --> Review[逐条审阅或手改]
  Review --> Working[独立工作稿快照]
  Working --> Export[预览与导出]
  Working --> Submitted[不可变投递快照]
```

新增模块按职责拆分，避免继续扩大现有组件：

| 路径（均为计划新增，除注明修改） | 职责 |
| --- | --- |
| `src/domain/tailoring.ts` | Zod 契约、证据状态、岗位稿和快照类型 |
| `src/domain/evidence.ts` | 原文分段、稳定引用、事实修订和引用有效性检查 |
| `src/domain/tailoring-guard.ts` | 数字口径、成果状态、职责升级等确定性风险检查 |
| `src/server/materials.ts` | 材料与事实候选的创建、确认、修订 |
| `src/server/tailoring.ts` | 岗位分析、对照、生成与候选提案的编排，不直接覆盖正文 |
| `src/server/resume-revisions.ts` | 工作稿修订、乐观并发控制、投递快照 |
| `src/server/ai/tailoring.ts` | 三类有界任务：材料整理、JD 对照、岗位稿生成 |
| 修改 `src/server/resumes.ts` | 岗位稿从快照读取；母版继续使用现有事实提炼路径 |
| 修改 `src/server/backup.ts`、`src/server/db/schema.ts` | 新数据备份与迁移 |
| 新增 `MaterialIntake.tsx`、`TailoringReview.tsx` 于现有组件目录 | 材料确认与逐条审阅；复用简历纸面 |
| 修改 `JobsWorkspace.tsx`、`ResumeWorkspace.tsx`、`src/content/zh-CN.ts` | 入口、状态、中文文案 |

### 13.2 数据模型与迁移

使用下一号迁移 `003_targeted_resume.sql`。迁移前保留备份，升级不删库；迁移与迁移记录在同一事务提交。表名为本轮设计约定，实现时使用对应 Drizzle 映射。

| 表/字段 | 核心内容与约束 |
| --- | --- |
| `source_materials` | 原文、来源类型、关联项目（可空）、内容 hash、创建时间；修改原文创建新修订，不改旧引用 |
| `evidence_facts` | `material_id`、原文字符范围、事实描述、`candidate/confirmed/rejected`、`planned/active/done/unknown`、职责和指标信息、修订号；只有 confirmed 可用于生成 |
| `job_analyses` | JD 快照、输入 hash、schema/prompt 版本、要求数组、证据对照、补问；结果不回写 JD |
| `tailoring_proposals` | 输入快照、分析 id、目标简历 id、基础修订号、候选条目、引用、风险、逐项处理状态、失效标记 |
| `resume_revisions` | 简历 id、递增修订号、`working/submitted`、完整文档 JSON、JD 与事实输入快照、时间；submitted 行不可修改 |
| `resumes.current_revision_id` | 当前工作稿；母版可以为空，不改变母版唯一约束 |

文档 JSON 使用 `ResumeDocumentV1`：档案快照、工作经历、技能、教育、排序后的项目和句子、句子证据引用、目标岗位、篇幅偏好。事实 id 引用外还保存当时原文和确认状态，避免材料修订或删除后投递记录失去解释依据。

每个岗位仍最多一个可编辑简历容器，可有多个历史投递快照。删除源项目不级联删除岗位稿和历史快照；删除岗位及历史记录需要明确确认影响范围。

迁移时，将现有投递版当时的档案、项目标题、排序和实际渲染句子固化为首份工作稿，保留手工改写，不自动调用模型。历史句子标为 legacy、未建立新证据映射；缺失信息不编造，待用户补充。母版仍可动态读取项目，但新的岗位稿不再以空 override 回退到实时项目句。

全量备份升级为 v2，覆盖新表和引用关系；继续接受 v1 并通过同一迁移映射补全。导入前验证版本、结构、唯一性与关联；整批导入事务提交，失败保持原库。v2 往返后工作稿、候选状态、快照和来源均一致。默认不保存完整模型请求日志或密钥。

### 13.3 生成契约、调用与失败处理

服务接口约定：

```ts
type EvidenceState = 'direct' | 'transferable' | 'not_shown' | 'confirmed_absent'
type FactStage = 'planned' | 'active' | 'done' | 'unknown'
type TextRef = { materialId: string; start: number; end: number; contentHash: string }
type Requirement = {
  id: string
  kind: 'responsibility' | 'must' | 'preferred' | 'context'
  text: string
  jdRef: { start: number; end: number }
  alternatives: string[] // 同一要求的可替代分支；无替代时为空
}
type RequirementAssessment = {
  requirementId: string
  state: EvidenceState
  factIds: string[]
  reason: string
}
type ProposedBullet = {
  id: string
  projectId: string
  text: string
  factIds: string[]
  requirementIds: string[]
  reason: string
}
```

所有模型结果使用 Zod 严格验证；引用由服务端从冻结原文回填。候选事实必须附实际存在的 TextRef，`confirmed_absent` 只能由用户明确回答派生。引用校验只能证明出处存在，不能证明改写完全忠实；发现语义不确定时标记待确认，不自行补强。

1. 用户保存 JD 与材料不依赖模型成功。现有自动分析需调整为可单独重试的显式任务。
2. 每次点击执行一个有界阶段，不使用工具调用。材料整理可跳过（已有确认事实时）；先完成 JD 对照，再生成岗位稿。
3. 首版单次 JD 上限 12,000 字符、单份材料 20,000 字符、单次确认事实总文本 30,000 字符；超限要求用户选择材料或拆分，不静默截断或声称支持任意模型上下文。提供较小材料重试入口。
4. 每个阶段总超时 120 秒，最多两次模型请求（首次加一次结构修复重试）；请求被取消时传递 AbortSignal。鉴权失败或限额错误不自动重试。生成执行阶段明确展示状态，输入控件保持可编辑。
5. cache key 包含完整 JD hash、事实修订及确认状态、配置模型标识、schema/prompt 版本和篇幅偏好，不含密钥。相同输入复用成功结果，不复用失败或已失效结果。
6. 请求开始冻结输入；返回时重新检查相关输入 hash、基础稿修订号。已变化的结果标记 stale，不可直接接受；旧正文不被覆盖。
7. 校验失败保留原稿，给出可读原因；含无效引用、新增数字或明确职责升级的句子不可作为安全生成句接受。语义无法可靠判定的句子必须人工确认；用户可手动改写并作为 user-authored 内容保存，不能伪造已验证标记。
8. JD、简历和材料均作为不可信数据传入，不得执行其中的指令、链接或代码。模型错误脱敏，响应不回显密钥。
9. 无密钥时仍可保存、手改和导出；fake provider 仅供测试，普通无密钥模式不能冒充真实生成。生成候选与原始材料不自动写回项目事实。

### 13.4 推荐、篇幅与编辑规则

- 先以必要条件和核心职责的证据覆盖推荐经历，再考虑优先条件、证据具体程度及内容重复；不因材料里有数字就自动加分，不因项目整体 active 就统一降低所有子成果价值。
- 向用户解释选择的要求和事实；缺乏有效材料时允许少推荐甚至不推荐，不能凑满三个项目。
- 默认生成目标 1 页、最多 3 个推荐项目，每项目目标 2～3 条；用户可选择 2 页。以上是初始内容预算，不保证字符数必然等于页数。
- 保留现有纸面，增加浏览器布局高度检测与超页提示；缩减次要内容需要预览确认，不自动截断、隐藏文本或缩小字体来假装达标。打印人工核对页数与分页；必要时用户调整页数目标。
- 同一事实面对不同 JD 可以采用不同重点，但没有证据时也允许内容不变，不能为了制造差异增加事实。
- 接受候选只更新当前工作稿并递增修订号，不修改事实、母版或其他岗位稿。用户手改后旧候选需要基于新稿重算；拒绝候选不触发重新生成。
- 自动保存完成后才导出；保存失败时阻止把旧稿当作最新稿导出。工作稿和投递快照均可按修订导出。

### 13.5 接口变更

| 接口 | 契约 |
| --- | --- |
| `POST /api/materials` | 保存纯文本原文；模型整理走独立动作 |
| `POST /api/materials/:id/extract` | 生成候选事实，返回候选及出处，不自动确认 |
| `PATCH /api/materials/:id/facts` | 批量确认/拒绝/修订事实，携带 expectedRevision |
| `POST /api/jobs/:id/tailoring/analyze` | 读取完整 JD 与指定确认事实，返回要求对照和最多 3 个补问 |
| `POST /api/jobs/:id/tailoring/draft` | 携带 analysisId、expectedInputHash、expectedRevision（首稿为 0）、pageTarget，持久化候选提案 |
| `POST /api/resumes/:id/proposals/:proposalId/apply` | 携带候选 id、接受/拒绝动作及 expectedRevision，事务写入新工作稿；409 表示输入或正文已变化 |
| `POST /api/resumes/:id/submit` | 基于 expectedRevision 创建不可变投递快照，不发送求职申请 |
| `GET /api/resumes/:id/revisions/:revision` | 读取指定工作稿/投递快照，供历史查看和导出 |

新接口沿用现有 HTTP 错误封装：400 输入错误、409 版本冲突、413 超限、503 未配置模型或上游不可用、504 阶段超时，附脱敏的业务 code。界面可重试失败阶段，无需重新录入。

现有 `POST /api/jobs/:id/resume` 保留创建/打开容器的幂等语义，不隐式生成或覆盖稿件。`PATCH /api/resumes/:id` 增加 expectedRevision，并同步当前文档快照；母版路径保持旧规则。现有 Markdown 与打印入口默认读取当前工作稿，可指定 revision 查看投递快照。

自动化门槛：`npm test`、`npm run typecheck`、`npm run build`、`git diff --check`。fake 模式覆盖业务行为，不作为真实模型质量证据。真实模型评估需记录模型标识、提示版本、样本、结果与失败案例，并由使用者主动触发；不把私人材料放入仓库。

探索验证主要观察从现有材料到「用户确认可投递」的耗时与返工；同时记录生成句采纳/修改/删除原因、第二个 JD 的素材复用情况、错误事实数量。尚无基线，暂不虚构提效百分比、固定耗时或过筛率目标。任何已知的新增事实失败案例必须修复或明确降级后再发布。
