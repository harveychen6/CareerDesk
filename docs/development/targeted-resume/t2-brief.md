# T2 — Materials and confirmed facts

Read first. Implement the material -> candidate -> explicitly confirmed fact backend, with simple reusable UI. Requirements in product.md 12.2–12.4, 13.2–13.3, T2. Existing T1 tables and contracts are available; adapt to their actual exports rather than duplicate. Do not modify snapshot/backup internals except integration bugs discussed with parent.

Own src/domain/evidence.ts, src/server/materials.ts, materials API routes, src/components/projects/MaterialIntake.tsx and material-specific tests. Material text max 20,000 characters; freeze source content and create separate material on edits (keep old references). Preserve exact source range, trim only candidate wording. Content hash server-owned. All refs must map to nonempty matching source ranges. Candidate wording is not automatically confirmed.

API desired:
- GET /api/materials?projectId= returns materials with fact candidates and original source; GET /api/materials/confirmed returns all currently confirmed facts (or exported listConfirmedFacts for server).
- POST /api/materials {content,projectId?} saves text. If projectId missing, create a project only when explicitly requested by createProject/title input; UI should let user create an experience for new materials without preexisting project. For simple product UX default new title from user, not model inventions.
- POST /api/materials/:id/extract triggers bounded extraction, not confirmation. No provider configured => 503 with saved text intact. May use independent new src/server/ai/materials.ts using a reusable structured model boundary later shared with T3. Coordinate protocol via report. Test fake provider must work offline; fake split real source lines into candidate facts, not fabricate content. Invalid/out of range refs rejected.
- PATCH /api/materials/:id/facts {expectedRevision, facts:[{id,status,text?,stage?}]} explicitly confirms/rejects or edits candidate. Stage planned/active/done/unknown; confirmed unknown can be used only as non-outcome pending clarification, recommended UI asks stage. Never silently import old project facts as confirmed. Provide import existing project's facts as source material so user can inspect/confirm.
- listConfirmedFacts() returns stable source refs + source text + project metadata needed for tailoring; validate refs at reading and keep material immutable. Parent T3 consumes this.

When creating a new experience/project from materials, ask user project stage explicitly (default active, not implicit done). Avoid default planned blocking every pasted experience: confirmed done subfacts in active project are allowed. MaterialIntake should show existing project's factsMarkdown as optional explicit import (not auto-confirm). Pending material fact edits preserve user's text when extract/list refresh returns. HTTP body revision values must be validated integers, not trusted casts.

MaterialIntake UI: reuse in project drawer and jobs later. Props projectId?:string, onChanged?:()=>void.
