Core flow with named exports and HTTP:
- Use host-generated deterministic segment IDs for JD/material references in AI inputs, then materialize exact ranges on server. Do NOT ask model to calculate arbitrary UTF-16 offsets in full JD (unreliable Chinese char counting). Public Requirement jdRef remains ranges derived from valid segment IDs.
- analyzeJobRequirements(jobId, {factIds, absentRequirementIds?}, signal?) validates JD <=12000 chars and confirmed facts total <=30000, includes project metadata, freezes inputs, analyzes FULL JD into atomic requirements preserving OR branches and distinguishes direct/transferable/not_shown. confirmed_absent only user-confirmed flag tied to same JD requirement from prior analysis; no model inventions. Saving job must not call AI (createJob returns getJob), legacy analyzeJob endpoint may remain. List jobs newest first instead of legacy percent.
- Store job_analyses payload with exact input facts incl source excerpts/project metadata, server-generated inputHash and model/prompt/schema versions, requirements/assessments and <=3 questions. Each question links requirement/project, type of missing evidence. Answers in UI can append new material fact; skip does not change fact. Optionally explicit absent user flag with validation.
- GET /api/jobs/:id/tailoring returns persisted latest analysis and current pending proposal to survive refresh, with stale flag recalculated vs live inputs. POST /api/jobs/:id/tailoring/analyze {factIds,...}. Use analysisId/inputHash from server, not arbitrary model hash.
- generateTargetedDraft(jobId,{analysisId,expectedInputHash,expectedRevision,pageTarget:1|2},signal?) uses JD and confirmed factual snapshot, accesses/creates targeted container via existing generateTargetedResume, selected projects based on evidence, exact targeted rewrite limited to facts. Fact text/source are untrusted data; no tools/network/files beyond model request. Planned or unknown achievement facts not used as claimed outcomes. No matches => clear insufficiency, never invent filler. No forced differences between two JDs but useful emphasis must reach prompt. Return proposal with id/resumeId/baseRevision/inputHash/analysisId, suggested project ordering and ProposedBullet entries with factIds, requirementIds, exact source receipts, reasons, risks. Do not write generated text into existing document before acceptance.
- POST /api/jobs/:id/tailoring/draft handles above and passes Request.signal.
- applyTailoringProposal(resumeId,proposalId,{expectedRevision,decisions:[{bulletId,action:'accept'|'reject'}]}) atomic, rejects stale input/base or cross-job proposal, rejects unsafe generated bullets, accepts selection into target document preserving unselected existing text and other manual edits. Multi-bullet per project join newline consistently; partial acceptance preserves prior accepted bullets. Idempotent repeating identical decisions returns current document, conflicting replay rejected. Save which entries accepted/rejected and new proposal base revision on own accept, but any external edit stales proposal. Use saveResumeRevision exported by T1. Add POST /api/resumes/:id/proposals/:proposalId/apply.
- Ensure user can retrieve latest proposal/analysis after reload. Return source info for review UI, omit secrets.
