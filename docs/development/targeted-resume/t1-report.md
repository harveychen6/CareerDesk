# T1 implementation report

## Delivered

- `003_targeted_resume.sql` adds `source_materials`, `evidence_facts`, `job_analyses`, `tailoring_proposals`, `resume_revisions`, and `resumes.current_revision_id`. Migration SQL, legacy snapshot conversion, and migration record execute in one SQLite transaction. Existing targeted drafts are captured before the DB is exposed to services; actual old included ordering and `paperBullet` fallback/overrides are retained. Master resumes remain dynamic.
- `src/domain/tailoring.ts` exports strict `EvidenceProvenanceSchema`, `ResumeProfileSchema`, `ResumeProjectSchema`, `ResumeDocumentV1Schema`, `ResumeDocumentV1`, and `ResumeProfile`. Documents store frozen profile (including photo), full job/JD, summary, page target, ordered project metadata, text, legacy/user provenance and per-bullet provenance. Legacy provenance is explicitly unmapped. Evidence provenance requires fact ID, material ID and source text.
- `getResume(id, revision?)` maintains existing UI fields while adding `revision` and `pageTarget` for a targeted draft. `updateResume` accepts `expectedRevision`, `profile`, `pageTarget`, summary, selected IDs and overrides; writes a new working revision transactionally. Missing expected revision remains accepted by internal callers for compatibility; HTTP PATCH requires it for targeted resumes. Existing snapshots are not refreshed when source records change. Explicit selection may add a subsequently created source project. Unknown IDs are rejected.
- `resume-revisions.ts` exports `RevisionConflict`, `ensureResumeSnapshots`, `currentResumeRevision`, `getResumeRevision`, `listResumeRevisions`, `writeResumeRevision`, and `submitResume`. A submit inserts a separate immutable-by-service submitted revision without changing the working pointer; the revision number increases across both kinds. HTTP submit and list/read history endpoints were added; PATCH and submit stale revisions return 409. Markdown and print accept `?revision=N`.
- Backup v2 exports all added tables and current pointers. Zod validates the full structure and types before writing; import checks IDs, references, revision ownership and uniqueness, document schema, JSON payload syntax, source SHA-256 hashes, and evidence ranges/project ownership. Import writes in one transaction; v1 imports are mapped through the same legacy snapshot function. Existing confirmation behavior is preserved.

## Integration contract for later stages

- Drizzle exports `sourceMaterials { id, projectId, title, content, contentHash, createdAt }`, `evidenceFacts { id, materialId, projectId, text, sourceStart, sourceEnd, status, stage, revision, createdAt }`, `jobAnalyses { id, jobId, inputHash, payloadJson, createdAt }`, `tailoringProposals { id, resumeId, jobId, analysisId, inputHash, baseRevision, payloadJson, createdAt }`, and `resumeRevisions { id, resumeId, revision, kind, documentJson, createdAt }`. `sourceMaterials.projectId` and evidence project IDs are nullable; deleting a project sets them null. Ranges use JavaScript UTF-16 offsets; content hashes use SHA-256 of UTF-8 content as lowercase hex. Analysis/proposal JSON is syntax-checked but its future semantic schema belongs to later stages.
- Snapshot document project entries expose `projectId`, `title`, `status`, `tags`, `org`, periods, `included`, `sortOrder`, `bullet`, `sourceBullet`, `bulletOverride`, `todoCount`, `provenance`, and `bullets: [{text, provenance}]`. The latter is a foundation, not yet an editing UI.
- Current UI still sends the legacy PATCH shape; T5 must send `expectedRevision` and write targeted profile edits through the resume endpoint instead of mutating only the global profile. Client handling for 409 and revision-aware history remains later work. This delivery does not implement materials, AI, proposal generation/apply, or application submission.

## Review fixes: overwrite protection and migration failures

- `importBackup` now requires confirmation when any meaningful profile field, customized settings, project/job data, nondefault resume or history, materials, facts, analyses, or proposals exist. The automatically created empty master, blank profile, and default settings do not trigger confirmation. A real-DB regression reproduced the previous missing-confirmation failure with a job and submitted revision but no name or projects; the corrected check preserves the existing data and a blank DB remains importable without confirmation.
- Legacy snapshots now use the same tolerant skills/tags parsing as the original UI: malformed JSON becomes an empty list and non-string array elements are filtered. The migration test covers both.
- SQLite initialization now keeps the connection local until migration and defaults succeed and closes it on error. A regression verifies repeated initialization continues to fail rather than exposing a partially migrated handle, and that 003 and its migration record roll back together.
- Red: backup test failed because no confirmation was raised; migration tests failed on invalid JSON and because the second initialization unexpectedly succeeded. Green: `npm test -- tests/tailoring-migration.test.ts tests/tailoring-backup.test.ts` passed 5/5; `npm run typecheck` passed.
